# weather-check

日本国内の任意の地点について、気象庁(JMA)などの公式データをWebFetch/Bashのみで取得し、正確な事実データとして整理する。**ブラウザ（Claude in Chrome）は使わない** — クラウドで完結させ、どのデバイスからでも同じ結果になるようにするため。tenki.jpのようなJavaScriptで内容を描画するサイトはWebFetchで取得すると発表日時がずれた古いキャッシュを返すことがあるため使わない。

このスキルは「データを集めて整理する」ところと、ゆきさん向けの日次ブリーフィングとしての出力までを担当する。呼び出し側（会話中の指示など）が地点や出力体裁を別途指定した場合はそちらを優先し、指定がない場合（`/weather-check` を引数なしで呼ぶ場合を含む）は下記の「デフォルトの呼び出し」に従う。

## Default invocation (no arguments or extra instructions)

これは日常的には毎日の天気・健康ブリーフィングとして使われる。呼び出し側から地点や出力形式について特に指示がない場合は、次を前提にしてよい：

- **対象地点**: `~/.identity/weather-location.yaml`（dotfiles-private で管理、`label`/`prefecture_code`/`area_code`/`latitude`/`longitude` を持つ）の既定地点を使う。ファイルがなければ地点をユーザーに尋ねる。ただし会話の文脈や前回のメモから、旅行中・滞在先が異なると判断できる場合はその地点に切り替える。判断できなければ既定地点のまま実施する。
- **実行環境**: クラウド実行専用。ブラウザ（Claude in Chrome）は使わない。
- **出力フォーマット**: 下記「デフォルトの出力フォーマット」に従う。

## Specify the location

呼び出し側から地点名が与えられたら、気象庁の府県予報区コードと緯度経度を確認する。わからない場合はWebSearchで「気象庁 予報区コード ＋地名」を検索して確認する。

## Today's date basis (common to all steps, important)

このスキルを実行するクラウドコンテナのシステムクロックはUTCであり、JSTではない。気象庁・環境省のデータはすべてJST（+09:00）基準で発表されるため、「本日の日付」「現在時刻」はUTCではなく**必ずJSTで**取得すること：

```
TZ=Asia/Tokyo date +%Y-%m-%dT%H:%M:%S%z
```

（Bashの`date`をタイムゾーン指定なしで使うとUTCの日付になり、JST 0時〜8時59分の間はUTCの日付が前日のままずれてしまう。この時間帯にスケジュールタスクが走ると、実際は最新のJSTデータなのに「発表日時が本日と一致しない」と誤判定し、警報・気温データなどを不要に省略してしまう。必ず`TZ=Asia/Tokyo`を明示するか、Pythonなら`datetime.now(ZoneInfo("Asia/Tokyo"))`を使うこと。）

## Freshness check approach (Steps 1-3, important)

このスキルが扱うJMA/環境省のデータには性質の異なる2種類がある。判定方法を混同しないこと：

- **複数日をカバーする予報データ（Step1）**: 気象庁の天気予報は1回の発表で「今日〜明日（〜明後日）」複数日分のデータをまとめて返す。したがって`reportDatetime`（発表時刻）そのものが本日と一致しているかではなく、**payload内の`timeDefines`（各要素ごとの実際の対象日時）にJST基準の本日・明日の暦日が含まれているか**で判定する。`reportDatetime`が前日発表であっても、`timeDefines`に本日の日付が含まれていればそのデータは有効（気象庁の予報はその範囲をカバーする設計のため）。逆に、`timeDefines`のどこにも本日の日付が存在しない場合のみ、その項目を「取得できませんでした」とする。
- **単一時点のスナップショット（Step2・Step3）**: 警報注意報や熱中症アラートは「現在の状態」を表す1時点のステータスであり、複数日分の配列を持たない。これらは`reportDatetime`（または発表日時表示）が**JST基準の現在時刻から24時間以内**であれば許容する（日付文字列の完全一致までは要求しない）。24時間を超えていれば「本日は情報を取得できませんでした」とする。

## Step 1: Fetch the forecast and temperature

`https://www.jma.go.jp/bosai/forecast/data/forecast/{府県コード}.json` をWebFetchで取得する。

- WebFetchへのプロンプトでは「today/tomorrowに要約せず、`timeDefines`の生のISO日時と`weathers`/`pops`/`winds`/`temps`の各要素を1対1でペアにして列挙して」と明示的に依頼すること。「今日/明日に要約して」と頼むと、発表日基準のtoday/tomorrowと実際の暦日がずれているケースで要素が黙って切り捨てられることがある（実際に発生を確認済み）。
- report[0]（短期予報）のtimeSeries[0]（weathers, winds）・timeSeries[1]（pops）・timeSeries[2]（対象地点のtemps）それぞれについて、`timeDefines`の日付を見てJST基準の「今日」「明日」に該当するエントリを個別に探し、値を割り当てる。**位置（0番目・1番目…）だけで「今日/明日」を決め打ちせず、`timeDefines`の実際の暦日との突き合わせを第一の判定基準にすること。**
  - temps配列は特に、発表時刻によって並び方の意味（今日の最高/最低、明日の最低/最高など）が変わるため、position決め打ちではなく必ず`timeDefines`の日付と突き合わせて「どの値が実際に本日・明日のものか」を機械的に確認する（生成AIによる要約の言い換えに頼らない）。
  - 今日・明日のいずれか一方（多くは「明日」）がpayloadの取得範囲外で見つからない場合は、その項目だけ「（明日分はこの発表の取得範囲外でした）」のように部分的に明記し、見つかった方（今日分）は通常通り記載する。全部をまとめて省略しない。
  - 今日の最高気温と最低気温が近い/同じ値になることがある（曇天・降雨で気温差が小さい日など）。異常値に見えても発表データをそのまま採用し、「気温差の小さい一日」のように自然な形で触れる程度でよい。

## Step 2: Fetch warnings and advisories

`https://www.jma.go.jp/bosai/warning/data/warning/{府県コードまたは地方コード}.json` をWebFetchで取得する。

- 発表日時（reportDatetimeまたはheadline内の日時）がJST基準の現在時刻から24時間以内であれば採用し、発表中の警報・注意報の種類と対象地域を記載する。24時間を超えている場合はこの項目自体を省略し、無理に記載しない。
- **既知の問題**: このエンドポイントはWebFetch経由だと、都道府県を問わず（宮城040000・青森020000・岩手030000いずれでも確認済み）数ヶ月単位で古いスナップショットが返ってくることがある。クエリ文字列を変えたキャッシュ回避を試しても解消しないことを確認済みで、気象庁側の障害というより取得経路側の長期キャッシュが疑われる（同時刻に軽量な`amedas/data/latest_time.txt`は正しく最新値を返すため）。したがって、**Step2は多くの回で24時間チェックに引っかかって省略される前提でよい**。無理な代替探しは不要。どうしても警報注意報の有無を確認したい場合のみ、呼び出し側の判断でWebSearch（「気象庁 {地域名} 警報 注意報」等）を補助的に使う手はあるが、このスキルの必須範囲には含めない。

## Step 3: Fetch heatstroke alert status

`https://www.wbgt.env.go.jp/alert.php` をWebFetchで取得する。

- ページに表示されている発表日時がJST基準の現在時刻から24時間以内であれば、対象都道府県のアラート発表状況（発表なし／熱中症警戒アラート／熱中症特別警戒アラート）を採用する。
- 24時間を超えている場合は「熱中症警戒アラートの発表状況は最新化されていなかったため参照できませんでした」と明記する。
- アラートの有無に関わらず、Step1で得た今日・明日それぞれの最高気温をもとに、次の目安で危険度を出す。**これは公式のWBGT実測値ではなく気温からの簡易目安なので、必ず「推定」と分かる表記を付ける**：
  - 35℃以上 → 危険 相当
  - 33℃以上 → 厳重警戒 相当
  - 30℃以上 → 警戒 相当
  - それ未満 → 注意〜安全
- 今日・明日の両方について危険度を出し、表形式でもよい。今日・明日のどちらかの最高気温がStep1で取得できなかった場合は、その日の分だけ算出できない旨を明記する。

## Step 4: Estimate the UV index

気象庁・環境省とも紫外線の常時更新API/ページを提供していないため、以下の目安で今日・明日それぞれ算出する。**実測値ではなく推定であることを必ず明記する。**

季節（月）・天気（晴れ/曇り/雨）・地点のおおよその緯度から目安を出す：
- 夏季（6〜8月）晴天 → 非常に強い〜極端に強い
- 夏季 曇天 → 強い程度（1段階下げる）
- 春・秋 → 中程度〜強い
- 冬季 → 弱い〜中程度
- 緯度が低い（沖縄など）場合は1段階上げる、高い（北海道など）場合は1段階下げる目安で調整する。

ピーク時間帯（10〜14時頃）の外出を避ける、日傘・帽子・日焼け止め（SPF30〜50程度）の目安も添える。

## Step 5: Calculate sunrise and sunset

ネットワークに依存せず、このスキルに同梱のスクリプトで計算する（気象庁・他サイトのページ取得は不要で、常に安定して使える）:

```
python3 <このSKILL.mdと同じディレクトリ>/scripts/sunrise_sunset.py <緯度> <経度> <YYYY-MM-DD> 9
```

例（東京、今日の日付）:
```
python3 scripts/sunrise_sunset.py 35.6812 139.7671 2026-08-25 9
```

計算値であり実際とは1〜2分程度前後する可能性がある旨を一言添えるとよい。

## Step 6: Heat shock information

外部データ不要。Step1の最低気温と季節（10月〜4月は特に強調）から、入浴時の急激な温度差に注意する旨の具体的なアドバイスを作る。

## Step 7: Other seasonal information (optional, low priority)

花粉（2〜5月）、PM2.5・黄砂（春）、インフルエンザ・感染症（流行期）などは、信頼できる出典が確認できた場合のみ記載する。無理に探しに行かず、確認できなければこの項目自体を省略する。台風情報は現時点で信頼できる構造化データ源が確認できていないため、必要なら呼び出し側の判断でWebSearchを使うこと（このスキルの必須範囲には含めない）。

## Date consistency rules (common to all steps)

- 「本日の日付」・「現在時刻」は必ずJST基準（`TZ=Asia/Tokyo date`など）で取得する。コンテナのシステムクロック（UTC）をそのまま使わない。
- Step1は「timeDefinesに本日・明日の暦日が含まれるか」、Step2・Step3は「発表日時が現在から24時間以内か」で判定する（上記「鮮度チェックの考え方」参照）。いずれの基準でも使えないデータは「本日は情報を取得できませんでした」と明記し、推測で埋めない。
- Step3(熱中症アラート)・Step4(紫外線)の気温・季節ベースの推定値は、この鮮度チェックの対象外だが、必ず「推定」と表記する。
- Step2・Step3で使うページは古いキャッシュを返すことがあるため、必ず発表日時を確認してから使う（Step2の既知の問題は同ステップの記載を参照）。

## Information this skill should return

- 今日・明日の天気、最高/最低気温、降水確率、風
- 熱中症: アラート発表状況（取得できた場合）＋気温ベースの危険度目安（推定）
- 紫外線指数の目安（推定）、今日・明日
- 気象警報・注意報（取得でき、発表から24時間以内の場合のみ）
- 日の出・日の入り（計算値）
- ヒートショックに関する季節的な注意点
- （該当あれば）その他の季節情報

呼び出し側が出力の体裁（見出しの付け方・絵文字・文体・締めの一言など）を別途指定した場合はそれに従う。指定がない場合は、次の「デフォルトの出力フォーマット」で最終的な回答をまとめること。

## Default output format (when unspecified)

- 日本語で出力する。
- 絵文字を適度に使って読みやすくする。
- 冒頭に「今日（日付）の{地点名} 天気ブリーフィング」と明記する（地点名は実際に使用した地点を入れる）。
- 次のセクションを見出しで区切る: 天気予報（今日＋明日）／おすすめの服装／熱中症情報／気象警報注意報（該当あれば）／日の出日の入り／ヒートショック情報／UV・紫外線情報／（該当あれば）その他の季節情報。
- 最後に「一言アドバイス」を1〜2文で締める。
- 簡潔にまとめつつ、行動につながる具体的な情報を優先する。
- 推定値（熱中症の気温ベース目安、紫外線指数の目安）や計算値（日の出日の入り）には必ずその旨（「推定」「計算値」）を分かる表記で付ける。
- 鮮度チェック（Step1はtimeDefinesに本日・明日の暦日が含まれるか、Step2・Step3は発表から24時間以内か）で使えないと判断した項目は「本日は情報を取得できませんでした」と明記し、推測で補完しない。

## Schedule task / unattended execution output

このスキルは毎日のスケジュールタスクなど、人が画面を見ていない自動実行コンテキストから呼ばれることも多い。その場合であっても、上記「デフォルトの出力フォーマット」に沿ったブリーフィング本文は、必ずセッションのchat応答（テキスト）として出力すること。省略したり、次に述べる通知手段の中だけで済ませたりしない。

呼び出し側のセッションがPushNotificationのような別途の通知手段を持っている場合、その通知にブリーフィング本文全文を詰め込むのは避ける。通知には今日の天気・注意点など一言程度の要点のみを渡し、全文はchat側で読む、という役割分担にするとゆきさんにとって扱いやすい。ただし、通知を送るかどうか・そこに何を書くかという判断自体はこのスキルの責務ではなく、呼び出し側（セッション側）の判断に委ねる。このスキルが保証するのは「ブリーフィング本文は必ずchatにフル出力する」という点のみである。
