# Restructure Obsidian Idea Notes

既存の `idea_notes/` を、情報を減らさず「1トピック1ファイル」へ再構成する。ファイル数、ファイル名、配置、見出し、表現は変更できるが、重複でない内容は判断条件や履歴を含めて保持する。

## Scope and authorization

- ユーザーが別のvaultを指定しない限り、`${HOME}/src/github.com/y-marui/obsidian-vault` を候補とし、存在を確認する。
- 対象範囲が `idea_notes/` 全体なのか、`idea_notes/finance` のような特定フォルダまたは特定ノートなのかを確認する。ユーザーが対象範囲を明示していない場合は必ず確認し、回答を得るまでインベントリ作成やファイル変更を始めない。既定vaultが決まっていても、対象範囲まで推測しない。
- vaultと対象ディレクトリの指示ファイルを、定められた順序で全文読む。特にノート構成、frontmatter、命名、Git運用の規則を優先する。
- 再構成の依頼は、対象範囲内のノートの作成、統合、分割、移動、置換、不要になった旧ノートの削除を許可する。ただし、対象外ノート、取り込み元、添付ファイル、commit、pushまで許可したとは扱わない。
- dirty worktreeの既存変更はユーザーのものとして保全する。自動コミットが発生しても巻き戻さず、開始時点と作業中のコミットを区別する。

## Preservation contract

保持対象は、再構成開始時に対象範囲へ存在した全 `.md` と、ユーザーが明示した取り込み元である。次を重複でない情報として扱う。

- 事実、数値、日付、固有名詞、URL、表、脚注、frontmatterの意味
- 方針、結論、条件、優先順位、運用方法、留保、未解決事項
- 候補、代替案、採用・見送り理由、比較軸
- 記述時点、旧スナップショット、変更履歴
- 本文から参照される画像や添付ファイル内の表・注釈など、文章化できる情報

文章の簡潔化や表形式への変更はよいが、断定の強さ、前提条件、例外、理由を弱めない。現在の情報へ更新しても、過去の表や判断が履歴として意味を持つなら、日付を付けて同じトピック内に残す。出典リンクを残すだけで、取り込んだ本文や表を削除したことにはしない。

完全に同じ意味の重複だけを統合できる。似ていても時点、条件、対象、根拠が違う記述は別情報として残す。誤りを見つけた場合は正すが、履歴上重要な旧記述は当時情報として区別する。

装飾用画像、記事末尾の宣伝、プラットフォーム固有の空要素など主題外の定型要素は、取り込み元を変更せず残し、再構成ノートから省ける。省いたものと理由を最終報告に記す。

## Topic boundaries

1トピックは、同じ問い、判断目的、または更新周期を共有する知識のまとまりとする。

- 独立して更新・判断できる内容は分ける。上位カテゴリが同じという理由だけで一つにしない。
- 同一対象の現行情報と過去スナップショットは、時系列の同一トピックとして一つのファイルに保持できる。
- 複数ノートに分けた場合は `[[wikilink]]` で関連付ける。
- `README.md` は索引であり、複数トピックを列挙してよい。各トピックの本文をREADMEへ退避しない。
- 同じトピックの重複ノートを作らない。既存ノートを自然に拡張できるなら統合を優先する。

## Workflow

### 1. Establish the baseline

変更前にGit状態を確認し、Gitリポジトリなら指示に従ってfetchする。次を一時的な作業台帳へ記録する。台帳はvaultへ保存しない。

- 基準コミット、開始時の変更、対象 `.md` の一覧とファイル数
- 各ファイルの見出し、箇条書き、表、リンク、添付参照
- 明示された取り込み元と、そこにだけ存在する情報
- 変更されない可能性があるファイルの内容ハッシュ

ユーザーが「再構成前」を指定した場合は、Git履歴から該当コミットを特定する。推測だけで基準を決めず、候補が複数あり結果が変わる場合は確認する。

### 2. Build a coverage inventory

原文をファイル単位で眺めるだけでなく、保持対象を意味の最小単位へ分ける。各項目に出所、内容、移動先、処理を対応させる。

処理は `そのまま保持`、`意味を保って統合`、`日付付き履歴として保持`、`主題外として除外` のいずれかとし、除外には理由を付ける。画像に表、数値、脚注がある場合は画像を実際に確認する。ファイル名やキャプションから内容を推測しない。

### 3. Design the destination structure

台帳を基にトピック境界を決め、旧ファイルから新ファイルへの対応表を作る。ノート数の増減を目標にせず、1トピック1ファイルと情報保持の両方を満たす最小構成にする。

再構成だけを依頼された場合、古い事実を暗黙に最新化しない。現行情報への更新も依頼された場合は、公式情報など直接的な一次情報で確認し、確認日を明記し、旧情報を履歴として保持する。

### 4. Rewrite and link

- vaultの規則に従ってfrontmatter、H1、ファイル名を整える。
- 条件、理由、候補、留保を結論だけへ縮約しない。
- 元ノートや取り込み元への参照は、来歴として有用な場合に残す。ただし参照だけを内容保持の代わりにしない。
- 分割・統合に合わせて関連リンクとカテゴリREADMEを更新する。
- 旧ノートを削除するのは、台帳上の全項目が移動済みであることを確認した後に限る。

### 5. Run the coverage gate

書き込み後、完成ノートを全文読み返し、基準時点と項目単位で照合する。

- 変更されなかったファイルは、可能なら内容ハッシュで同一性を確認する。
- 分割・統合したファイルは、台帳の全項目に移動先があることを確認する。
- 過去の表を保持する場合は、行数だけでなく元表との差分も確認する。
- 情報を含む画像の表題、数値、脚注が本文へ反映されていることを確認する。
- 取り込み元を変更しない方針なら、そのGit差分がないことを確認する。
- ファイル数の一致や総行数の増加だけを、情報保持の証拠にしない。

脱落、意味の弱化、誤った列見出し、古いリンクを見つけたら、その場で修正して再照合する。

### 6. Validate the vault

- 各トピックノートがfrontmatterとH1を持ち、READMEの例外を考慮して検査する。
- 各ファイルが1トピックで、重複ノートや切れた内部リンクがないことを確認する。
- `git diff --check` と `git status --short` を実行する。
- 自分の変更、先行変更、自動コミットを区別する。

## Report

次を簡潔に報告する。

- 変更前後のノート構成と、統合・分割・移動の対応
- 情報保持を確認した方法と、復元または訂正した項目
- 意図的に省いた主題外要素と、その保存場所
- 1トピック1ファイル、frontmatter、H1、リンク、差分検査の結果
- commit、push、自動コミットを含むGit状態

「情報は減っていない」と報告するのは、coverage gateを通過した場合だけにする。
