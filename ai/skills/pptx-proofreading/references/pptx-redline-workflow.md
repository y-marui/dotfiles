# pptx-redline comment workflow

- `.pptx` の調査とコメント追加は、その場でPythonやOOXML操作スクリプトを書かず、`pipx` で導入された `pptx-redline` コマンド（実体は [y-marui/python-docx-redline](https://github.com/y-marui/python-docx-redline)）で行う。作業開始時に `pptx-redline --help` で `inspect`、`add-comments-batch`、`list-comments`、`validate` が利用できることを確認し、不足している場合は使い捨て実装へ戻らずパッケージの更新が必要と報告する。編集前に `pptx-redline inspect` で対応するテキスト範囲とオブジェクトのIDを取得し、`list-comments` で既存コメントを確認する。複数の指摘はコメント定義JSONへまとめ、`add-comments-batch` で一括適用する。出力は原本と異なる新規ファイルにし、1件でも対象を一意に決められない場合は出力を作らない。
- スライド本文の修正文案は、修正対象の現行語句そのものを `match` に指定し、原則として正確なテキスト範囲へコメントを付ける。必ず `slide` で対象を狭め、同一スライド内でも一致が複数ある場合は `shape_id` または1始まりの `occurrence` を併用する。大きな文やテキストボックス全体ではなく、修正判断に必要な最小の語句へアンカーする。
- 画像内の文字、図、グラフ、空のテキストボックスなど、正確なテキスト範囲へ付けられない対象は、`inspect` の結果とレンダリング画像を照合し、その対象自体の `object_id` と `slide` を指定する。対象を特定できないという理由だけでスライド全体へ付けない。`slide_level: true` は、特定の語句やオブジェクトでは表せないスライド全体の構成上の指摘、またはspeaker noteだけへの指摘に限る。固定座標やスライド全体への暗黙のフォールバックは使わない。
- コメントには問題と具体的な修正案を簡潔に書く。テキスト範囲やオブジェクトが対象を示すため、通常はスライド番号や位置を本文へ重ねて書かない。既存のコメント著者になりすまさず、実行中のコードエージェント名を `--author` で明示する。名前を確認できない場合、汎用の既定名で記録せずユーザーに確認する。
- `pptx-redline` が対応しないグループ化図形、表、SmartArtなどに繰り返し遭遇した場合は、コメント位置を推測する補助スクリプトを増やさず、`pptx-redline` 側への機能追加を検討する。一回限りの補助スクリプトは、対象とアンカーを安全に特定でき、既存コメントと原本内容の保持を検証できる場合だけ使用する。数式を含む図形（`mc:AlternateContent` へ退避された図形を含む）自体は `inspect`/`add-comment` の対象になるが、数式そのものの記号は文字として一致させられない（不透明なプレースホルダー扱い）ため、数式に直接アンカーする指摘は `object_id` または `slide_level` で行う。
- コメント追加後は `pptx-redline list-comments` で各コメントの `slide`、`shape_id`、`start`、`length` または `object_id` を読み戻し、コメント定義JSONと照合する。続けて `pptx-redline validate <output> --original <source>` を実行し、スライド順、本文、ノート、メディア、既存コメントが保持されたことを確認する。既存の未対応アンカーなどで追加または検証が停止した場合は回避せず、コメント付きコピーを納品しない。
