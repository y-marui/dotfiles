# PPTX Proofreading

Microsoft PowerPoint (`.pptx`) のスライド本文と speaker note 内の発表原稿を、著者の意味と技術的意図を保ちながら校閲する。PPTXには安全で互換性のある変更履歴の経路がないため、明らかな言語上の修正を含め、既定では本文を直接編集せず具体的な修正案をコメントとして残す。

## Read the review context

レビューや編集の前に、対象デッキと同階層の次のファイルを順に探す。この手順で、デッキがGitリポジトリ内にある必要はない。

- `PROOFREADING.md` は、同一フォルダ内のDOCX・PPTXに共通する方針である。先頭の有効な `@<relative-path>` 行は、`$OBSIDIAN_ROOT/writing/` を基準にした執筆・校閲ガイドの必須参照である。各参照先を本文より先に読む。`@` 行には相対パスだけを許可し、絶対パス・`..` を含むパス・先頭以外の `@` 行は参照として扱わない。
- `@` 行がある場合は、通常のシェル初期化を読まずに `zsh -f` で `$HOME/.ai/zsh_path.local` だけを source し、そこで export された `OBSIDIAN_ROOT` を参照先の解決に用いる。この設定ファイルは AI 用のパス設定に限定し、対話処理、標準出力、ネットワークアクセス、ファイル変更を含めない。雛形は `dotfiles/ai/zsh_path.local.example` に置く。
- `@` 行があるにもかかわらず `$HOME/.ai/zsh_path.local` が存在しない・読めない、source 後も `OBSIDIAN_ROOT` が未設定、または `$OBSIDIAN_ROOT/writing/<relative-path>` が存在しない・読めない場合は、校閲・編集を開始しない。設定ファイルのパス、未設定の変数名、または解決しようとした完全パスを示して、設定または参照の修正をユーザーに求める。同名ファイルの探索や、ローカルルールだけでの続行はしない。
- `PROOFREADING.pptx.md` は `PROOFREADING.md` の後に、PPTXだけへ適用する。ここに書かれた `@` 行は外部参照として解決せず、通常のローカル指示として扱う。
- 指示は、skillの既定、`PROOFREADING.md`、`PROOFREADING.pptx.md`、今回のユーザー依頼の順に適用する。競合時は後のものを優先する。
- ローカルルールが未検証の科学的または実質的な判断を要求する場合は、スライドとノートを保持して代わりにコメントへ具体案を入れる。
- フォームや雛形の未記入欄は、ユーザーが明示的に依頼しない限り補完・編集しない。
- ユーザーがファイルを添付またはドロップした場合、元の場所を確実に特定でき、読み書きできるときは、その場所の原本を処理対象とし、校正コピーも同じ場所に保存する。元の場所を特定できない、アクセスできない、または同じ場所に保存できない場合は、添付コピーを原本の場所とみなさず、編集前にユーザーへ処理対象と出力先を確認する。
- 同階層の `proofreading/HANDOFF.md` がある場合は、ローカルルールの後に読み、対象デッキ・版・更新時刻が一致する作業状況だけを再開時の補助情報として使う。引き継ぎメモは恒久ルールではなく、現在のデッキ状態と矛盾する場合は現物確認を優先する。
- 納品時に、適用したローカルファイル（`PROOFREADING.md` / `PROOFREADING.pptx.md`）を明記する。どちらも存在しない場合は、このskillの既定手順で進める。

## PPTX safeguards and workflow

- 原本は保持し、ソースディレクトリ直下には原本と `<stem>-proofread-<mode>-<YYYYMMDDHHMM>.pptx` 形式の最終校正コピーだけを置く。作業途中のPPTX、コメント定義JSON、展開XML、PDF、レンダリングページ、検証出力は `<source-directory>/proofreading/cache/<source-deck-stem>/` に、再現に必要な補助スクリプトは `<source-directory>/proofreading/scripts/<source-deck-stem>/` に保存する。
- 編集前に、スライド、ノート、既存のコメント・スレッドコメント、リンク、埋め込みオブジェクト、図表、数式、カスタムXML、コメント関係を確認する。既存コメントを保持できると確認できない場合、コメントを追加する校正コピーを作らず、指摘一覧を返す。
- `.pptx` の調査とコメント追加は、その場でPythonやOOXML操作スクリプトを書かず、`pipx` で導入された `pptx-redline` コマンド（実体は [y-marui/python-docx-redline](https://github.com/y-marui/python-docx-redline)）で行う。作業開始時に `pptx-redline --help` で `inspect`、`add-comments-batch`、`list-comments`、`validate` が利用できることを確認し、不足している場合は使い捨て実装へ戻らずパッケージの更新が必要と報告する。編集前に `pptx-redline inspect` で対応するテキスト範囲とオブジェクトのIDを取得し、`list-comments` で既存コメントを確認する。複数の指摘はコメント定義JSONへまとめ、`add-comments-batch` で一括適用する。出力は原本と異なる新規ファイルにし、1件でも対象を一意に決められない場合は出力を作らない。
- スライド本文の修正文案は、修正対象の現行語句そのものを `match` に指定し、原則として正確なテキスト範囲へコメントを付ける。必ず `slide` で対象を狭め、同一スライド内でも一致が複数ある場合は `shape_id` または1始まりの `occurrence` を併用する。大きな文やテキストボックス全体ではなく、修正判断に必要な最小の語句へアンカーする。
- 画像内の文字、図、グラフ、空のテキストボックスなど、正確なテキスト範囲へ付けられない対象は、`inspect` の結果とレンダリング画像を照合し、その対象自体の `object_id` と `slide` を指定する。対象を特定できないという理由だけでスライド全体へ付けない。`slide_level: true` は、特定の語句やオブジェクトでは表せないスライド全体の構成上の指摘、またはspeaker noteだけへの指摘に限る。固定座標やスライド全体への暗黙のフォールバックは使わない。
- コメントには問題と具体的な修正案を簡潔に書く。テキスト範囲やオブジェクトが対象を示すため、通常はスライド番号や位置を本文へ重ねて書かない。既存のコメント著者になりすまさず、実行中のコードエージェント名を `--author` で明示する。名前を確認できない場合、汎用の既定名で記録せずユーザーに確認する。
- `pptx-redline` が対応しないグループ化図形、表、SmartArt、数式などに繰り返し遭遇した場合は、コメント位置を推測する補助スクリプトを増やさず、`pptx-redline` 側への機能追加を検討する。一回限りの補助スクリプトは、対象とアンカーを安全に特定でき、既存コメントと原本内容の保持を検証できる場合だけ使用する。
- コメント追加後は `pptx-redline list-comments` で各コメントの `slide`、`shape_id`、`start`、`length` または `object_id` を読み戻し、コメント定義JSONと照合する。続けて `pptx-redline validate <output> --original <source>` を実行し、スライド順、本文、ノート、メディア、既存コメントが保持されたことを確認する。既存の未対応アンカーなどで追加または検証が停止した場合は回避せず、コメント付きコピーを納品しない。
- 事実、科学、方法論、論理、数値、図表の解釈、主張の強さに関わる変更は、本文・ノートへ直接適用しない。コメントに「例」として修正案を示し、著者の専門的判断が必要であることを明記する。
- ユーザーが本文またはノート原稿への直接編集を明示的に依頼した場合だけ、原本を保持した校正コピーへ最小限の変更を行う。既存コメント・ノート境界・レイアウトを保持し、変更箇所と検証結果を報告する。
- PPTX操作・レンダリングでComputer Useを使わない。必要になった場合は、実行前に必要性を説明してユーザーの了承を得る。

## Speaker notes

speaker note は、次の順序と区切りを既定とする。

```text
発表原稿（校閲対象）

--- メモ（校閲対象外） ---
個人メモ…
```

- 1つだけ存在する完全一致の独立行 `--- メモ（校閲対象外） ---` より前を発表原稿として校閲する。区切り行とそれ以降のメモは、一切レビュー・編集・引用しない。
- 区切りがない場合、ノート全体を発表原稿として扱う。
- 区切りが複数ある、行の前後に本文がある、文字が異なるなど、境界を一意に判定できない場合は、ノートを変更せず「speaker note の原稿・メモ境界を確認してください」と報告する。
- 区切りが正しくても、ノート全体または区切り前が箇条書きの断片、TODO、連絡先、個人的注記、資料リンク、断片的な引用などを主とし、発表原稿よりメモらしい場合は、原稿として校閲してよいか確認する。原稿とメモが混在して見えて範囲を一意に定められない場合も、推測で校閲・編集せず要確認として報告する。
- ノート原稿への提案はノート本文に書き込まず、対応するスライドの `slide_level: true` コメントに残す。コメントは `Speaker note / 原稿:` で始め、対象の現行語句を引用し、具体的な修正案を示す。スライド本文の指摘と同じコメントへ混在させない。
- 出力前にノートXMLを原本と比較し、区切り行とメモ部分が完全に保持されたことを確認する。直接編集をしていない場合も、抽出したノート原稿・メモ境界をレビュー記録として検証する。

## Cross-format review rules

レビュー前に、共通参照 [../_proofreading-common/review-principles.md](../_proofreading-common/review-principles.md) を全文読む。言語・文体の判定、意味・数値・引用の保護、各言語の校閲観点、著者判断を要する問題へのコメントは同参照を適用する。

## Select the mode

ユーザーが指定したモードを使う。モードが指定されていない場合は、校閲・編集を開始せず、次の選択肢を提示して選択を確認する。`Layout-Check` は文章校閲の深さとは独立しており、1〜3の選択に `+ Layout-Check` として明示的に組み合わせられる。レイアウト確認を暗黙に追加しない。

1. `Light`: 誤字脱字、文法、句読点、明らかに不自然な表現だけをコメントで指摘する。
2. `Standard`: Lightに加え、明瞭さ、簡潔さ、自然な表現、用語の一貫性をコメントで改善する。
3. `Deep`: Standardに加え、論理、構成、学術文体、主張と根拠の対応をレビューする。
4. `Layout-Check`: 本文を編集せず、組版と表示だけを確認する。

- `Light`: 誤字脱字、文法、句読点、明らかに不自然な表現だけをコメントで指摘する。
- `Standard`: Lightに加え、明瞭さ、簡潔さ、自然な表現、用語の一貫性をコメントで改善する。既定値はこれである。
- `Deep`: Standardに加え、論理のつながり、曖昧さ、スライド間の構成、学術文体、読者が誤解しやすい点を確認する。事実関係・主張・論拠・方法・結論は、文書内の整合性、根拠の十分性、因果関係、目的との対応、引用・図表との対応をレビューする。意味、論拠、根拠、構成の変更を要する問題はコメントとして扱う。
- `Layout-Check`: スライド本文を編集せず、PPTXをPDFへ変換してPNGへレンダリングし、全スライドを視覚確認する。文字化け、フォント置換、文字・図表の欠け、重なり、はみ出し、コメント表示、余白、スライド番号を確認し、問題は位置と内容を報告する。

`Deep` で科学的文書をレビューする場合は、対応する `references/<domain>.md` があれば追加で適用する。文書種別の判定に確信が持てない場合は、推測でファイルを選ばずユーザーに確認する。

## Verify and deliver

1. `pptx-redline list-comments` で追加コメントの件数・著者・アンカー種別を読み戻し、テキスト範囲のコメントが `shape_id` と正の `length` を、画像・図形へのコメントが意図した `object_id` を持つことを確認する。意図せず `shape_id`、`length`、`object_id` がすべて空のコメントはスライド全体へのコメントなので、コメント定義と一致しなければ作り直す。
2. `pptx-redline validate <output> --original <source>` でPPTX構造と原本内容の保持を検証する。
3. PDFへ変換し、PNGとして全スライドをレンダリングして1枚ずつ視覚確認する。コメントだけの追加なら、原本と出力コピーのスライド描画が同一であることも確認する。画像・図形コメントは、`inspect` のオブジェクト名とレンダリング上の対象を照合する。
4. 生成物が開け、スライド・コメント・ノートが読み取れることを確認する。原本が未変更であること、既存コメントが保持されたこと、speaker note の区切りとメモが保持されたことを確認する。可能な場合はPowerPointでも代表的なテキスト範囲コメントとオブジェクトコメントのマーカー位置を確認し、構造検証だけで表示位置を確認済みとしない。
5. 納品時に、使用モード、対象範囲、適用したローカル方針、出力コピー、コメント数、テキスト範囲・オブジェクト・スライド全体ごとの件数、既存コメントの扱い、ノート原稿の扱い、PDF/PNG確認範囲、PowerPointでの表示確認の有無、未解決事項を簡潔に報告する。

## Retain durable proofreading knowledge

- DOCXとPPTXに共通するレビュー原則は `../_proofreading-common/review-principles.md` に追加する。
- PPTXだけの安全な作業規則・実装手順はこの `SKILL.md` に追加する。
- 特定の文書種別だけに関わる内容レビューの観点は `references/<domain>.md` に追加する。
- 文書またはフォルダ固有の規則は、共通なら `PROOFREADING.md`、PPTXだけなら `PROOFREADING.pptx.md` に追加する。
- コンテキストの記録・引き継ぎをユーザーが依頼した場合は、`pptx-proofreading-handoff` に従う。一回限りのデッキ内容、一時的な作業状態、推測的な結論、今回だけに限定されたユーザー指示は永続化しない。
